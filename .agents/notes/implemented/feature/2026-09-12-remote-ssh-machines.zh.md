# Agent Note: 工作区可以在已保存的 SSH 计算机上运行

Status: implemented

[English](2026-09-12-remote-ssh-machines.md) | 中文

## 问题

工作区以前只能使用运行 DSH 的计算机。工具和代码仓库位于其他计算机上的用户必须离开应用，或在远程计算机上维护另一套 harness。

## 决策

`remote-machines` Host 服务保存具名 SSH 配置，并且只向浏览器发送脱敏后的配置视图。密码、私钥和私钥密码不会出现在列表响应中。用户可以保存密码或私钥、使用 SSH Agent 自动验证，或输入仅在当前 Host 生命周期内保留且不写入磁盘的密码。更改身份验证方式时，系统会删除属于旧方式的 secret。

远程工作区路径使用包含计算机标识的内部前缀。共享文件系统和 subprocess 服务识别此前缀，并通过 SFTP 和 SSH 路由文件操作、命令及交互式终端通道。本机路径继续使用现有的本机实现。

首次连接会探测 host key 并显示其 SHA-256 指纹。用户必须信任这个准确的指纹，工作区才会启动。确认信任时系统会再次探测 host，以拒绝在检查和确认之间发生变化的 key。仍有已注册工作区引用时，系统不允许删除对应的远程计算机。

Web 客户端新增远程计算机设置分区、composer 控件旁的计算机选择器，以及按计算机分组的工作区行。打开已有远程工作区时也会执行与新路径相同的指纹检查。

## 考虑过的替代方案

**在每台机器上运行独立 Harness。** 这种方式让执行留在各服务器本地，但用户必须切换应用并重复配置，无法从同一个 DSH 实例管理这些工作区。

**首次连接时不经确认就信任主机。** 这种方式少一个设置步骤，却无法区分目标服务器与被拦截的首次连接，因此客户端要求用户明确确认指纹。

## 后果

一个 DSH 实例可以管理本机工作区以及已保存的 Linux 或 macOS SSH 计算机。探测时仍能识别 Windows SSH host，但客户端会拒绝创建远程工作区，因为当前命令 runtime 使用 POSIX shell 约定。
